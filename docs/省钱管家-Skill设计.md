# 省钱管家 Skill 设计（实现用）

> 面向开发者/用户本人的实现设计稿：给出决策流程、判定点与踩坑清单，照着写代码即可。

## 1. 角色定位
当「所有人都说随便、但每个人又都有一点要求」时，帮发起人把一场无法推进的点餐对话，变成一张能确认、能下单、最省钱的单。

## 2. 决策流程（核心判定点）

```
用户输入（餐品 + 约束 + 取餐方式）
   ↓
[判定1] 取餐方式：到店 / 得来速 / 麦乐送 / 企业团餐
   → 到店/得来速：不传 beCode；麦乐送：传 beCode
   → 参数矩阵 beType · orderType · beCode 三者联动，传错直接报错
   ↓
[判定2] 拉真实数据：门店 + 菜单 + 可用券（领全部可领券 + 卡包已有券合并）
   ↓
[判定3] 组候选池：单品 / 套餐 / 每张券 / 积分兑券 / 团餐满折 全部进池
   ↓
[判定4] 券能不能用：券绑定的 productCode 是否在购物车里
   → 车里没对应商品 → 券静默失效，用户以为没优惠（重点排查）
   ↓
[判定5] 买一送一：BOGO 绑专用 SKU（不在常规菜单），必须用专用码下单
   → 挂普通商品报错，挂促销码被忽略
   ↓
[判定6] 券能不能叠：一单一张券；套餐与 1 张券可同单
   → 多券同单报 600022，必须拆单
   ↓
[判定7] 用券还是套餐：两者都实算，比大小
   → 只盯券会漏掉更省的套餐方案
   ↓
[判定8] 团餐凑单：enjoyable.balance 给出的门槛差额
   → 差一点点到下一档折扣，提示要不要加购凑单
   ↓
[判定9] 热量约束（可选）：营养库 160 项，处理「中杯/大杯」「2块/4块」名称歧义
   ↓
全部金额只认 calculate-price 返回值 → 讲解 → 用户确认 → create-order
```

## 3. 关键实现红线（每条都是实测踩坑）
| # | 红线 | 后果 |
|---|---|---|
| 1 | Skill 不算价，一切金额只认 `calculate-price` | 多步算术 + 约束推理，大模型算不准；价格错一位就是事故 |
| 2 | 到店不自动套券，必须显式挂券 | 不挂 = 优惠 0 |
| 3 | 券生效三条件：有券 + 车里有对应商品 + 显式传 couponId | 缺一个优惠为 0 |
| 4 | 一单一券；套餐 + 1 券可同单 | 多券同单报 600022 |
| 5 | BOGO 用专用 SKU（如中薯条买一送一 = 9900012387） | 挂普通商品报 600012 |
| 6 | 积分不直接抵现，只能换券再抵 | 直接抵现不可行 |
| 7 | 取餐方式参数矩阵（beType·orderType·beCode） | 到店传 beCode 报错 |
| 8 | Token 只用环境变量占位 | 提交真实 Token 违规且会被刷 |

## 4. 可信边界（宁可信不过，不信错）
- 报价 = 收银台价：下单前二次核价，宁可少报优惠，不给假低价；
- 下单、领券、改账户等操作前必须用户明确确认；
- 售罄、优惠失效、无门店等异常要显式处理，不能静默。
